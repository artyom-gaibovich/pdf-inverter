# Правила чтения документов

Правила обращения к документам через `Read`, `Grep`, `Glob`: гейт чтения перед каждым вызовом,
границы контекста задачи и строгий гейт для файлов секретов.

## Таблица правил

| ID | Правило |
|----|---------|
| READ-001 | Перед КАЖДЫМ вызовом `Read`/`Grep`/`Glob` пройти гейт: цель чтения (файл или каталог) должна быть указана явно — в запросе пользователя, правилах проекта или тексте исполняемого сценария команды либо сабрутины |
| READ-002 | Если путь не указан явно — СТОП: инструмент не вызывается, у пользователя запрашивается явное разрешение с обоснованием (какой документ, зачем, что именно требуется) |
| READ-003 | «Похоже, пригодится для задачи» не является прохождением гейта; критерий — явное указание пути, а не оценка полезности |
| READ-005 | Сценарий команды или сабрутина даёт право читать только те пути, которые называет поимённо |
| READ-006 | Ссылка на документ как на источник подхода не даёт права читать его выходные файлы и отчёты |
| READ-008 | Файлы с секретами (`.env` и его варианты, `.ssh/`, `.gh/`, файлы учётных данных) проходят строгий гейт: читаются только по явному разрешению пользователя, выданному под конкретную задачу; упоминание пути в правилах, конфигурации или сценарии разрешением не является |

> **Примечание:** нумерация правил сохраняет исторические идентификаторы, поэтому в ней есть пропуски.
> Номер правила неизменен: ссылки вида `READ-008` из других документов остаются действительными.

## Гейт чтения [READ-001..003]

**[READ-001]** Перед КАЖДЫМ вызовом `Read`, `Grep` или `Glob` сначала ответь на вопрос:

> **Путь указан явно?** — цель чтения (файл или каталог) поимённо названа в запросе пользователя, в правилах проекта или в тексте исполняемого сценария команды либо сабрутины (Subroutine, SUB).

**[READ-002]** Если ответ **НЕТ — СТОП.** Не вызывай инструмент. Запроси у пользователя **явное разрешение с обоснованием**: какой документ, зачем он нужен и что именно из него требуется. Дождись ответа. Без разрешения чтение не выполняется.

**[READ-003]** «Похоже, что пригодится для задачи» — это **НЕ** прохождение гейта. Критерий READ-001 требует явного указания пути, а не твоей оценки полезности. Вызывать `Read`/`Grep`/`Glob` без прохождения гейта запрещено.

Типичные нарушения — чтение по собственной инициативе:

- сгенерированные проектные артефакты и результаты предыдущих итераций;
- чужие выходные файлы и соседние документы того же каталога.

> **Примечание:** правила проекта, подключённые в системный промпт (`CLAUDE.md`, `AGENTS.md` и перечисленные в них документы), считаются названными явно: их чтение предписано самим промптом.

## Границы правила [READ-005..006]

**[READ-005]** Сценарий команды или сабрутина даёт право читать **только те пути, которые называет поимённо**. Если сценарий читает `A`, это не разрешает по своей инициативе открыть смежный `B`.

**[READ-006]** Ссылка на документ как на источник **подхода** — правил или порядка действий — отсылает к его содержанию, но **НЕ** даёт права читать выходные файлы и отчёты, полученные при применении этого документа.

> **Примечание:** правило согласовано с ограничениями на git-операции чтения — см. [git-rules.md](./git-rules.md).

## Строгий гейт для секретов [READ-008]

**[READ-008]** Файлы с секретами не открываются по обычному гейту [READ-001](#гейт-чтения-read-001003).
Для них действует **строгий гейт**: чтение выполняется только по явному разрешению пользователя,
выданному под конкретную задачу.

Под правило подпадают:

- `.env` и любые его варианты (`.env.local`, `.env.production`, `.env.*`);
- содержимое `.ssh/` и `.gh/` — приватные ключи, токены доступа к репозиторию;
- файлы учётных данных агента: `.credentials.json`, каталог профилей `.claude-accounts/`.

Разница с [READ-001](#гейт-чтения-read-001003) — в том, что закрывает гейт:

| Гейт | Что достаточно для чтения |
|------|---------------------------|
| Обычный [READ-001] | Путь назван явно: в запросе пользователя, правилах проекта или сценарии команды |
| Строгий [READ-008] | Только явное разрешение пользователя под текущую задачу |

Упоминание пути **не является** разрешением, даже если путь назван поимённо: ни `env_file: .env`
в `docker-compose.yml`, ни ссылка из README, ни строка в правилах проекта, ни собственный совет
агента «посмотреть, что в `.env`» строгий гейт не закрывают.

### Что делать вместо чтения

Задача почти всегда требует не значений, а состава ключей — его даёт шаблон:

- имена переменных и их назначение брать из `.env.example`, он не содержит секретов;
- нужное значение запрашивать у пользователя либо использовать через окружение процесса,
  не печатая его;
- проверять наличие переменной, а не её содержимое: `[ -n "$TOKEN" ]` вместо вывода `$TOKEN`.

> **Внимание:** прочитанный секрет попадает в контекст сеанса и в историю диалога целиком —
> отозвать его оттуда нельзя. Поэтому правило запрещает само чтение, а не только вывод значения.

**Если файл секретов всё же прочитан** — по разрешению пользователя или по ошибке — значения
не пересказываются в ответе, не пишутся в файлы проекта, не попадают в сообщение коммита
и не отправляются во внешние сервисы.

## Пример

Запрос пользователя: «поправь `README.md`».

| Действие | Гейт | Итог |
|----------|------|------|
| `Read README.md` | путь указан явно | пройден — читать можно |
| `Read` соседнего документа каталога «вдруг там контекст» | путь нигде не назван | НЕ пройден → СТОП, запросить разрешение |
| `Grep` по отчёту, на который сослался сценарий команды как на источник подхода | READ-006: ссылка на подход не открывает выходные файлы | НЕ пройден → запросить разрешение |
| `Read .env`, чтобы узнать порт сервиса | файл секретов, строгий гейт READ-008 | НЕ пройден → взять состав ключей из `.env.example`, значение спросить |
